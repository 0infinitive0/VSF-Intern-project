# Phase 6: Refresh run and publish

## Overview

Execute the harness against the current system, write the findings by hand from what the run
actually shows, publish the report pair, and freeze a new baseline. This is the phase that produces
the "updated metric performance" the plan exists for — everything before it is machinery.

**This phase splits at step 5.** Steps 1-4 run `--limit 1` and are always in scope: they prove the
whole pipeline produces a valid report end to end. Steps 5-12 need the full dataset and are
**gated on the user explicitly asking for a full run** (plan.md's execution constraint). Do not
start the full pass because the one-sample pass looked good — stop at step 4 and ask.

## Requirements

- Functional: a `--limit 1` run of both layers with LLM metrics on, producing a complete valid
  report pair — this is the phase's default deliverable.
- Functional (gated): one full run, both layers, LLM metrics on, against the live corpus —
  **only on explicit user request.**
- Functional: a hand-authored findings document, written from this run's diagnosis — `report.py`'s
  docstring is explicit that findings are never generated, and that constraint holds here.
- Functional: a hand-authored caveats document covering the harness/production deviations this plan
  introduced.
- Functional (gated): a fresh `baseline.json` frozen against the current `dataset_hash`. A baseline
  frozen from a one-sample run would be worse than no baseline — it would silently become the
  reference every later run is diffed against. Never write it from a limited run.
- Non-functional: the redaction check passes before anything is committed.
- Non-functional: the run's own cost is reported, using the machinery this plan just built —
  the first thing the new cost accounting should be able to answer is what it cost to measure.

## Architecture

**Cold-cache first, then warm.** Run once with `.ragas_cache/` cleared to get true judge cost and
true judge latency, then optionally re-run warm to confirm score stability. The cold run is the one
that gets published; the warm re-run is a determinism check, not a second data point. Record which
is which — `cost_this_run` vs `cost_cold_cache` will be identical on the cold run, which is itself
a useful confirmation the two figures are computed correctly.

This cold/warm pair applies at `--limit 1` too, and is worth doing there first: it exercises the
cache-hit accounting for a couple of calls instead of a whole dataset, and a bug in that logic is
much cheaper to find on two calls than on fifty.

**What one sample can and cannot establish.** A `--limit 1` run proves the pipeline: the harness
imports, drives a turn, scores it, aggregates, prices, renders a report, and passes redaction. It
cannot produce a percentile (`degenerate: true` by Phase 3's own rule), BR-10 probe coverage, a
worst-10 table, a stage-success rate, or a defensible threshold proposal. The one-sample report is
therefore a *pipeline artifact*, not a measurement — write it to a scratch path or label it clearly
so it is never mistaken for a published result, and never let it overwrite `baseline.json`.

**What this run must be compared against.** The 2026-08-11 report is the last published one, but
it is not a clean comparison: the agent plane was rewritten between then and now, and Phase 2 may
have re-adjudicated two conversations. State that explicitly in the findings rather than presenting
a stage-success delta as if it measured the same thing twice. The honest comparison is
retrieval-side (same golden set, same functions, if `dataset_hash` is unchanged); the e2e side is a
new measurement of a new plane.

**Findings are diagnosis, not description.** The existing report's findings section is the model to
follow: each finding names what was observed, what caused it, and what was done or is proposed —
`ragas-20260811-0732.md`'s finding 3 traces a VI/EN gap to a dataset-authoring artifact and proves
it with an isolated test. A findings list that just restates the tables is not worth the section.

**Latency and cost get findings too.** With P50/P95/P99 available for the first time, the specific
questions worth answering in prose: is the P95/P50 ratio wide enough to indicate a slow tail rather
than uniform slowness? Which turn class dominates cost per conversation? Is retrieval or generation
the larger share of a turn's latency? A table alone does not answer any of those.

## Implementation Steps

1. Pre-flight: confirm Ollama/Cloudflare embedding reachability, `backend/.env` completeness, and
   that the live corpus still covers the golden set's five destinations and the
   `2026-07-01..07` availability window the conversation scripts depend on
   (`ragas-20260811-0732.md` Caveats flags this as a known expiry risk). A run against a drifted
   corpus produces numbers that describe the corpus, not the system.
2. Clear `.ragas_cache/` and run
   `eval/.venv-eval/bin/python eval/run_ragas.py --limit 1 --out <scratch>.json` (both layers, LLM
   metrics on). One retrieval query, one conversation. Seconds to a minute, negligible spend.
3. Generate a report pair from it with placeholder findings/caveats and confirm the whole chain
   holds: latency section renders with `degenerate: true`, cost section shows real app-side and
   judge-side tokens with a priced total, redaction check passes, transcript written.
4. Re-run the same limited pass warm and confirm `cost_this_run` drops while `cost_cold_cache`
   stays put — this is the cache-hit accounting check, and it is far cheaper here than at full
   scale.

**Gate — stop here and report to the user.** Steps 1-4 establish the pipeline works.
Everything below spends a full dataset pass and only runs when the user asks for it.

5. Run the full pass: clear `.ragas_cache/` and run `eval/run_ragas.py` with no `--limit`, both
   layers, LLM metrics on. Expect minutes, and real spend.
6. Read the raw JSON before writing anything: worst retrieval queries, harness failures, latency
   outliers, and the most expensive turns. Diagnose the outliers — an unexplained P99 is a finding
   waiting to be written, not a number to publish.
7. Write findings and caveats as separate markdown files. Caveats must include, at minimum: the
   price-table `as_of` date, the judge cache state, the sample sizes behind each P95/P99, the
   Phase 2 stage re-adjudication if one happened, Cloudflare embeddings being token-counted but
   unpriced, and live-corpus non-hermeticity. There is deliberately no `stream_usage` caveat —
   Phase 1 fixed that in production, so eval and production now stream identically.
8. Generate the report pair with `report.py --findings ... --caveats ...` and confirm the redaction
   check passes.
9. Re-run warm to confirm score stability; record any movement in caveats as measured variance
   rather than explaining it away.
10. Freeze the baseline with `--save-baseline` and confirm `dataset_hash` matches the run.
11. Verify `--compare-baseline` against the fresh baseline round-trips cleanly (deltas all zero on
    quality, latency/cost deltas printed as informational).
12. Update `plan.md` status and run `detect_changes()` before committing.

- [x] A report generated from it renders every section, with latency marked `degenerate: true`.
- [x] Cost shows non-zero app-side and judge-side tokens with a priced total and printed divisors.
- [x] The warm re-run shows `cost_this_run` below `cost_cold_cache`.
- [x] The redaction check passes on the raw JSON.
- [x] `baseline.json` is **not** modified.
- [x] The user is told the pipeline is verified and asked whether to spend the full pass.

Gated scope (steps 5-12, only on explicit user request):

- [ ] A full two-layer run completes with LLM metrics on and zero harness errors (harness
      *failures* — conversations not reaching their expected stage — are results, not errors).
- [ ] The published report has populated Latency and Cost sections and hand-authored findings that
      diagnose rather than restate.
- [ ] Cost per retrieval query, per e2e turn, and per conversation are all present with divisors.
- [ ] The run's own total cost is stated in the report.
- [ ] `baseline.json` is frozen against the current `dataset_hash`, and `--compare-baseline`
      round-trips it cleanly.
- [ ] Caveats cover every harness/production deviation this plan introduced.
- [ ] The findings state plainly which comparisons against the 2026-08-11 report are valid and
      which are not.

## Risk Assessment

| Risk | Mitigation |
|---|---|
| The live corpus drifted and the golden conversations' hardcoded date window no longer has availability, blocking every conversation | Step 1 checks this before spending a run. If it has expired, the date window is refreshed and the change is logged in `eval/datasets/README.md` — the prior report already documents this exact failure happening twice |
| A cold-cache full run is expensive and may need repeating after a bug is found | This is what the step 1-4 / step 5+ split exists for: every bug that a one-sample pass can catch is caught before the full run is proposed. The `--limit` flag exists for exactly this |
| The one-sample report gets mistaken for a published result, or overwrites the real one | Step 2 writes to a scratch `--out` path, never the default `eval/results/ragas-<ts>.json`, and step 4's criteria assert `baseline.json` is untouched |
| e2e stage success drops sharply versus 2026-08-11 and gets read as a regression caused by this plan | The graph rewrite happened between the two runs and is the far more likely cause. Findings must attribute the change to the plane change, or investigate before publishing — publishing an unattributed drop is worse than publishing late |
| Findings get written from the tables instead of from diagnosis, and the report becomes decorative | The prior report is the bar; step 3 requires reading the raw JSON before writing prose |
| The new baseline freezes numbers from a run with an undiagnosed anomaly | Step 7 comes after step 3's diagnosis on purpose. An anomaly that cannot be explained is a reason not to freeze yet, and that call belongs to the user |

## Results — steps 1-4 (2026-08-18)

**Step 1, pre-flight.** Models resolve to the committed config (`gpt-5.1-2025-11-13`,
`gpt-5-mini-2025-08-07`); embeddings reach Cloudflare `@cf/baai/bge-m3` (1024-dim vector
returned); all five golden destinations resolve in the live corpus. The conversation scripts'
`2026-07-01` window is now in the **past** (today is 2026-08-18) and still returns availability —
itineraries built successfully on every replay — so the expiry risk the 2026-08-11 report flagged
has not bitten. Worth revisiting before a full pass if hotels start coming back empty.

**Steps 2-3, cold pipeline run** (`.ragas_cache/` cleared, `--limit 1`, both layers, LLM metrics
on, written to a scratch path — `eval/results/` untouched):

| layer | scope | calls | input | output | cost |
|---|---|---|---|---|---|
| retrieval | app | 2 | 510 | 286 | $0.000700 |
| retrieval | judge | 12 | 12112 | 651 | $0.002208 |
| e2e | app | 5 | 4563 | 523 | $0.007574 |
| e2e | judge | 3 | 1929 | 166 | $0.000388 |

Report pair generated, **redaction check PASS**, every section rendered: single-observation
families carry `⚠︎` and `degenerate: true`, both cost scopes are populated and priced, divisors
printed. Note the retrieval judge is the expensive half at this scale (12 calls / 12k input
tokens for one query — `LLMContextPrecisionWithReference` and `ContextRelevance` fan out per
retrieved context).

**Step 4, warm re-run — cache accounting confirmed:**

| run | state | hits | cost_this_run | cost_cold_cache | estimated |
|---|---|---|---|---|---|
| cold | cold | 0/2 | $0.002208 | $0.002208 | false |
| warm | warm | 2/2 | $0.000000 | not derivable | true |

Cold: the two figures match exactly, confirming they are computed consistently. Warm: cost drops
to zero and every operation is accounted as a hit. `cost_cold_cache` is `not derivable` rather
than a number because *every* scoring operation hit the cache, leaving no observed call to
extrapolate from — the honest consequence of Phase 1's "a cache hit fires no callback" finding
(see Phase 4 Results, Deviation). A partially-warm run does produce a projection.

**Two bugs found and fixed by running the chain rather than assuming it:**
1. `report.py` could no longer be executed directly (`ModuleNotFoundError: harness`) — the Phase 4
   `harness.cost` import broke a documented entry point. Fixed with the same `sys.path` bootstrap
   `smoke_check.py` uses.
2. The judge-cache line rendered a `None` cold-cache cost through `_usd()`, printing
   `UNPRICED (neuron-billed)` — an embeddings label, meaningless for a cache figure. Now prints
   `not derivable` with the reason.

`baseline.json` was **not** modified (verified); all scratch artifacts removed and
`eval/results/` restored to its committed state.

## Gate

Steps 1-4 prove the pipeline end to end. Steps 5-12 spend a full dataset pass — 30 retrieval
queries and 9 conversations of live LLM and Supabase traffic, cold cache — and per plan.md's
execution constraint they run only on an explicit request for a full run.

Rough projection from the one-sample cost, stated as arithmetic and not as a promise (per-query
and per-conversation cost both vary with query complexity and conversation length):
30 × $0.0029 retrieval + 9 × $0.0080 e2e ≈ **$0.16**, plus minutes of wall clock.
