01

Verdict

Keep Railway for the short-lived demo path. Move to AWS when durable PostgreSQL, private networking, secret references, and operational boundaries are real requirements—not merely because AWS is the larger platform.

The AWS plan is sound as a staged target, but it must not be reported as deployed. Start with App Runner + RDS; keep Airflow/dashboard local or restricted until the operational need is proven.

05

Gaps before AWS can ship

01 / boundary

Cost and access

Choose region, account boundary, IAM roles, budget alert, and shutdown plan before provisioning.

02 / data

RDS path

Prove App Runner-to-RDS connectivity, apply scripts/database_schema.sql, load data, and record counts.

03 / operations

Admin surfaces

Decide whether Airflow/dashboard are local fallback or private ECS services. Never expose Adminer by default.

Important distinction: the current Railway service returning “ready” proves container/API reachability. It does not prove durable hotel-data persistence or cloud Airflow readiness.
06

Recommended next move

Phase order

API + RDS first

  1. Provision ECR and RDS with budget controls.
  2. Wire secret references and private connectivity.
  3. Deploy App Runner and run the two public smoke checks.
  4. Write image rollback and snapshot restore steps.
Defer

Airflow + dashboard later

Keep the existing Compose topology for local/admin work until cloud scheduling, persistence, and access control are explicitly required.

This keeps the AWS plan aligned with its own scope challenge: ship the API/data layer first.
