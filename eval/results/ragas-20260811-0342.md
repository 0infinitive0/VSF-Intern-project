# RAGAS evaluation — 20260811-0342

## What this run says

This is the first real run of the harness against the trip-planner pipeline (2026-08-11). Two
layers were measured: retrieval quality (44 hand-authored queries) and end-to-end grounding (12
scripted conversations through the real agent). **Correction note:** an earlier pass of this run
used travel dates (August-December 2026) outside the corpus's only populated room-availability
window and wrongly concluded hotel search was broken for *any* date. Re-run with dates inside
the real window (2026-07-01 to 2026-07-07, confirmed by the project owner) surfaces the true
picture below — hotel search works, but two narrower, still-real bugs block most conversations
from completing.

## Findings, ranked

### 1. Room/pricing availability data only covers 2026-07-01 to 2026-07-07 (HIGH — data gap, not a code bug)

Verified directly: `search_hotels_with_rooms(..., start_date=X, end_date=Y)` returns 5+ valid
hotels for any date pair inside 2026-07-01..07, and **zero** for every date pair tested outside
it (August, September, December 2026, January 2027 all tried). This is a corpus/data-pipeline
limitation, not an application bug — but it means any conversation using a "realistic" future
date (which is what a real user would type) currently gets zero hotels, unless the demo is
scoped to this specific week. Flagging for whoever owns the data pipeline: either backfill wider
date-scoped availability, or the product needs to constrain/default date pickers to the covered
window so users don't hit an unexplained dead end.

### 2. A pending guided question can misapply a later turn's number as its answer, producing degenerate filters (CRITICAL — real code bug)

Traced directly, reproduces consistently: after the hotel-budget guided question ("Bạn muốn mức
giá khách sạn khoảng nào?") is asked and the user's *next* message answers something else
entirely (e.g. "Khởi hành ngày 01/07/2026" - a date, not a price), the pipeline still extracts a
number out of that message and applies it as `max_price`. Traced case: `"01/07/2026"` → the
extractor pulled `2026` (the **year**) as `max_price=2026` VND — a price so low no real hotel
qualifies, so the search returns zero results and surfaces the misleading "no hotel with valid
coordinates" error. This affects most of this run's conversations, because they all follow the
same natural order (destination+duration → people count [triggers the budget question] → start
date), and it's the same class of bug as finding 1's misleading error message: the guided-question
state isn't cleared or re-validated against what the next message actually answers.

### 3. Hotel selection does not resolve ordinal language ("khách sạn đầu tiên" / "thứ hai")

Once real hotel results are retrieved (bypassing findings 1-2), replying "Chọn khách sạn đầu
tiên" ("pick the first hotel") does not select option 1 - the tool re-lists the same options and
asks the user to answer with an explicit number or the hotel's name. This may be an intentional
disambiguation safeguard rather than a bug, but it does not match BR-03's "natural conversation"
framing, and a real user who says "the first one" (a completely ordinary way to answer) hits a
loop. `conv-nhatrang-couple-3d`'s transcript shows this concretely: 5 real hotels retrieved,
"Chọn khách sạn đầu tiên" re-lists them instead of selecting.

### 4. One conversation (`conv-crosslang-hyatt-danang`) ran clean end to end

Reached its exact expected stage (`hotel_options`) with real retrieved hotel contexts and scored
faithfulness/relevancy. This is the one clean success in this run and confirms the harness's own
mechanics (context capture, stage derivation, scoring) work correctly once the pipeline itself
behaves — the earlier all-failures result was the pipeline hitting findings 1-2, not a harness
defect.

### 5. Retrieval layer (Layer 1, unaffected by findings 1-2 - no dates involved): severe generic-name duplication in the kids-play attraction category

Dozens of attractions across all 4 destinations share the near-identical name "Khu vui chơi trẻ
em" (children's play area) at distinct physical locations. No single instance is a principled
must-retrieve answer for a query in this category - corrected during golden-set authoring (see
`eval/datasets/README.md`'s adjudication log); flagged as a corpus-quality finding in its own
right.

### 6. Two BR-10 cross-language queries fail even with the hotel's exact name in the query

`hotel-crosslang-libertycentral-vi` ("Liberty Central Saigon Centre giá bao nhiêu") and
`hotel-crosslang-novotel-vi` ("khách sạn Novotel Premier bên bờ sông Hàn") do not surface their
target hotel in the top 10, despite the hotel's brand name appearing near-verbatim in the query.
See `eval/datasets/README.md` for the full adjudication.

### 7. A landmark's colloquial name and its formal database name don't reliably co-locate in the embedding space

"Đại Nội Huế" (colloquial name for the Huế Imperial Citadel) returns zero attractions at the
production `match_threshold=0.4`, even after `extract_search_filters` strips the query to the
bare 2-word "Đại Nội" - the citadel's own formal name ("Hoàng Thành Huế"/"Kinh thành Huế") never
surfaces, not even "Ngọ Môn" (the citadel's own gate) until the threshold is manually dropped to
0.2. See `eval/datasets/README.md`.

## Why existing tests never caught findings 1-2

`backend/tests/test_chat_turn_characterization.py` fakes `recommend_hotels` in every one of its
test cases (`session.tools.recommend_hotels = _FakeTool(...)`, `_FakeTools.recommend_hotels =
_never_called(...)`) — the whole suite characterizes routing and stage-derivation logic only, and
never exercises the real `search_hotels_with_rooms` → `select_hotel_candidates` → Supabase RPC
path, or the guided-question answer-extraction path, that findings 1-2 live in. That's a
structural blind spot unit tests built this way cannot close on their own — exactly the class of
gap this e2e harness (real agent, real Supabase, no mocks) exists to catch.

## What is NOT a finding here

- No hotel or attraction name was invented anywhere in the 12 replayed conversations, including
  every turn after a search failure. The system correctly refuses rather than hallucinating when
  it has nothing to ground an answer in (BR-07 held under failure).
- Non-LLM retrieval precision/recall numbers (see below) are real but should not be read as a
  verdict on embedding quality in isolation — see Caveats.

## Caveats

- **The `faithfulness_by_turn_class` / `response_relevancy_by_turn_class` aggregates below are
  empty, but real per-turn scores exist in the raw data.** 0/12 conversations reached their exact
  expected stage this run, and by this harness's design (see plan Phase 4), every turn from a
  harness-failed conversation is excluded from the quality aggregates — a conversation that ends
  wrong shouldn't get averaged in as if it succeeded. Several turns that *did* retrieve real hotel
  contexts before their conversation later stalled on findings 1-2 scored real, non-trivial
  faithfulness values (e.g. 0.25-0.5, see `eval/results/transcripts/conv-nhatrang-couple-3d.md`)
  - visible in `eval/results/ragas-<ts>.json`'s per-turn rows, just not in the aggregate. Re-run
  after findings 1-2 are addressed before expecting a non-empty aggregate.
- **Templated-output inflation is only partially assessable this run** — a handful of `template`
  turns (recommend_hotels) did produce real output and got scored, but not enough of them to
  draw a stable template vs. generated comparison yet.
- **Small N.** 44 retrieval queries and 12 conversations are enough to catch structural bugs
  (this run did, twice) but not enough to estimate a stable population-level precision/recall
  number.
- **Live-corpus non-hermeticity.** Both layers hit live Supabase; a corpus update between runs
  changes scores independent of any code change. One hotel drift was already observed between
  the fixture and live data during Phase 2 authoring (2026-08-10). The room-availability window
  (finding 1) is itself a form of this: it will change or disappear as the data pipeline evolves,
  and conversation scripts pinned to 2026-07-01..07 will need updating when it does.
- **Judge variance.** `temperature=0` is not a cross-session determinism guarantee against
  provider-side model updates; only within-cache-window re-runs are exact.
- **VI/EN judge asymmetry was not isolated this run** — too few conversations completed on either
  language to compare meaningfully.
- **Non-LLM retrieval precision is measured against a hand-adjudicated golden set that itself
  changed shape during authoring** (several `expected_ids` were broadened to `acceptable_ids`
  after the first retriever run surfaced legitimate alternates the author didn't anticipate —
  see `eval/datasets/README.md`). The numbers here reflect that corrected set, not the original.
- **Cost is wall-clock + call-count based, not token-metered.** `ragas==0.3.9`'s token usage
  parser was not verified against the installed OpenAI client in this run; see run metadata for
  measured latency instead of a dollar figure.
- **This report went through two corrections during authoring.** The first e2e pass used travel
  dates outside the corpus's actual availability window and mis-attributed the resulting
  zero-result searches to "no date-scoped data exists at all" — wrong; the real constraint is a
  narrow 7-day window (finding 1), caught by the project owner reviewing the draft report.
  Numbers and findings below are from the corrected, third pass.
